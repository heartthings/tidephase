## 一、为什么要做这个系统

### 1.1 缘起：您的三页手稿

2026-09-29/30，您写了三页手稿，定义了一套**投资认知系统"观势"**：

```
外部输入（新闻/行情） → 认知库（基础认知=您逐字输入 + 历史认知=系统自分析）
    → 决策输出（思路分析/预测/应对方案/报告 四类）
    → 验证回流（每日对答案 → 回写置信度 → 周复盘校准 → 修订能力圈）
    → 反思精进（10-08 您补环指示：人类精进靠反思） → 回到认知库 ↺
```

手稿第 3 页是**"数据方案"**——观势的每一环都要吃数据：盘前简报要隔夜全球行情，盘中哨兵要指数/板块/情绪快照，验证引擎要证伪指标的实际序列，周复盘要基率和校准统计。**这一页的工程落地，就是本系统。**

三个前提决策（观势规格 v2.0 开篇即定）：①**自建时序数据库**；②**数据源用公开 API 体系**（您 D5 裁决确认：无付费行情）；③**数据要完善**——全市场、全域、可追溯。

### 1.3 为什么非做不可：三个旧底座撑不住

| 旧底座 | 问题 |
|---|---|
| 观势过渡库 SQLite（market.db） | 单文件、320 日回填就到顶；无并发写、无分区压缩、无审计字段；只是个原型 |
| **lovetrade 遗留 Java 系统** | 您的既有生产项目，但：业务接口和 11 个定时采集任务耦合在一个服务里；催化雷达写坏无法修正（无 PUT/DELETE）、长文本字段截断/写入即 500；MySQL root 口令明文硬编码在脚本里；数据只有它自己有，观势经它的 HTTP API 二传手取数 |
| 分散在各 skill/脚本的取数逻辑 | 各拉各的源、口径不一、无 source 标记、错了无从追溯、重复采集互相打架 |

结论：观势要长期跑"决策→验证→反思"闭环，必须有一个**统一、可靠、可追溯、带认知域写回能力**的专属数据层；同时把 lovetrade 的数据资产（26 表 43.9 万行）、功能面（8 块）、定时任务（11 个活任务）全部迁进新架构，让老系统体面退役。

七个问题，每个都有对应的机制设计（机制详见第三章）：

| # | 问题 | 系统的答案 | 验收口径 |
|---|---|---|---|
| 1 | **数据不完善**：观势要看全市场+全球+情绪+资金+宏观 | 12 数据域 + 日历域，69 表 5 视图；A 股全市场日线约 5,200 只/日、全球 21 品种、板块 11,318 行、雷达事件 29.7 万行 | 近 250 交易日 stock_daily 缺失率<0.1%，index_daily 零缺失 |

| 3 | **不可追溯**：出了错不知道数据从哪来、什么时候进的 | 每行带 `source + ingest_ts`；原始响应 raw 归档留一年（可解压重放）；ingest_log 全链路审计 | 任意行可追溯 source+ingest_ts+校验状态 |

| 5 | **消费混乱**：谁都能连库，权限和稳定性失控 | **API-first**（您 D7 裁决确认）：观势只走 `127.0.0.1:8787` HTTP，三档 token（read/write/admin）可分权可吊销；永不公网 | 76 API 路径全走鉴权；库账密零扩散 |
| 6 | **认知闭环没有载体**：预测写在哪、怎么对答案、怎么算基率 | D12 认知预测域：prediction 全生命周期（pending→hit/miss/partial/expired）+ base_rate 基率聚合（五口径）+ calibration 校准视图（Brier 分）+ **反思层**（reflection_pack 四段证据包，"无证据包的反思=无效"） | 10-11 实测：343 条预测结果分布与源库逐项吻合、calibration_view 15 行非空、观势已实写 7 条反思 |
| 7 | **遗留系统退役**：lovetrade 的数据、功能、定时任务要无损搬家 | 全量迁移工程（W1 数据 / W2 API / W2b 作业 / Z7-ext 催化雷达三表）+ 五波验收门槛（W5：对账平+新作业连跑 3 交易日+观势干跑 PASS+您 Web 验收）才停服；**stop 不 rm、卷保留** | 逐表行数对账平；观势 22 命令替代矩阵全有着落 |

## 三、系统是如何设计的

### 3.1 总体架构（实测运行态）

```
数据源（腾讯/东财/龙虎开盘啦/AKShare/新浪/mootdx/财联社/巨潮/HKEX…全公开API）
    ↓
dsched 调度服务（APScheduler + job_registry 38作业/35启用 + 漏跑检测）
    ↓
dworker 采集工作器（9个源适配器 + 降级链 + 熔断 + 行级校验 + quarantine + raw归档）
    ↓
TimescaleDB (PG16) market_tsdb —— 12域 69表+5视图（hypertable分区+压缩+保留策略）
    ↓
data-api（FastAPI，仅 127.0.0.1:8787，76路径，三档token）
    ↓
观势 skill（盘前简报8:15/盘中哨兵*/15/收盘分析17:30/验证引擎18:15/周复盘周五16:00）
    ↑______________ D12 写回（认知/预测/反思）形成闭环 ______________|
```

- **四容器**：`market-tsdb`（库，宿主 15432）/ `market-sched`（调度）/ `market-worker`（采集）/ `market-api`（服务）。docker compose 拉起，**代码即仓库挂载**（改代码 restart 容器即生效，不存在第二份运行代码）。
- **仓库**：`/home/hello/application/dev/market-datalayer`，git 27 commits、70 个 Python 文件 15,656 行、30 份施工/验收报告全留痕（12:5x 实测）。

### 3.2 存储设计：为什么是 TimescaleDB

观势规格给出 7 条选型要求，对比 ClickHouse/QuestDB/DolphinDB/InfluxDB 后选定 TimescaleDB：

| 要求 | TimescaleDB 满足方式 |
|---|---|
| 标准 SQL（skill 可读） | 就是 PostgreSQL 16，观势侧 SQL 语义零学习成本 |
| upsert 幂等 + 乱序容忍 | PG 原生 `INSERT ... ON CONFLICT`；hypertable 乱序写入无碍 |
| 分区 + 压缩 | hypertable 按时间自动分区；stock_daily 年增约 135 万行、分钟线千万行/年，压缩策略已配 |
| 保留策略 | 日频全留、分钟 3 年、tick 不留 |
| 连续聚合 | 日 K 由分钟聚合物化视图（stock_minute_5m 等 5 视图） |
| 备份/PITR | WAL-G 方案曾建，**您 D4 裁决"不用备份"后停用**；恢复路径=raw 归档（一年）+源端重采，成本半日~一日（风险已留痕，不再劝） |
| 权限模型 | **四角色隔离**：duser_writer（采集写）/ duser_reader（API 只读+30 秒超时熔断）/ duser_admin（DDL 运维）/ duser_d12writer（仅认知/预测/基率写） |

### 3.4 采集管道设计（可信的四道闸）

```
调度触发（六时间窗：盘前07:30-08:00 / 盘中15min / 收盘15:10-16:30 / 事件批 / 次日补采07:00 / 双源复核17:00）
  → 日历门禁（休市日不落业务表，只写 SKIP 日志——10-10 周六误写 5224 行事故后上线）
  → 源降级链（mootdx/腾讯 → 龙虎 → 东财 → AKShare → 新浪/同花顺 → 快照兜底 → MISS+次日补采）
      · 429/403 反应式熔断（人为限速已按您 D8 裁决删除）
      · retry×3 退避 [2s,5s,10s]（10-09 竞价间歇断连事故后上线）
  → 行级校验（pct 与 close 自洽、量级合理、日历对齐）——不过 → quarantine 隔离，不入库
  → upsert 幂等入库（每行 source+ingest_ts）
  → raw 原始响应归档（gz，留一年，可重放）
  → ingest_log 记账（OK/MISS/SKIP，禁止静默）
```

**验收三件套纪律**（每次采集完成的定义）：ingest_log 有 OK 行 + 目标表当日 COUNT>0 + raw 归档可解压。三缺一不算完成——这是从"注册≠实装"事故里长出来的规矩。

### 3.5 服务层设计：API-first（您 D7 裁决维持，五条论证）

观势曾反问"skill 直连库是不是更好"，结论是**不直连**：①权限面——直连=库账密扩散进每个下游工作区，API 三档 token 可分权可吊销；②写管控——D12 写入校验（认知 ID 前缀 F/C/H/M、防误写业务表、日历门禁）只能在 API 层；③稳定性——观势重查询直压库会拖垮采集写入，API 只读角色带 30 秒超时熔断隔离两侧；④演进缓冲——加列/改分区时 API 契约不动则 skill 不坏；⑤成本近零——同机 localhost 一跳微秒级。唯一例外（ad-hoc 复杂分析）将来用受控 query 端点解决，仍不直连。

端点面（76 路径，12:5x 实测）：通用查询 `/data/{table}`（白名单管控）+ meta 三件套 + 情绪/全球聚合 + **D12 认知域 13 端点**（cognition/prediction/impact/active_message/system_state 读写全套）+ 反思三端点（reflection_pack/route_map/reflection）+ lovetrade 兼容面 31 端点（catalyst/topic/market/note/report/calendar/home/auth）+ 校准/基率。

### 3.6 认知闭环设计（本系统区别于普通行情库的核心）

**预测生命周期**：观势写预测（必带证伪条件 falsify + 检查日 check_date + 创建时相态 regime_at_create）→ 验证引擎 18:15 对答案 → result 五值（hit/miss/**partial 计 0.5**/expired 不计分母/invalid）回写 → base_rate 按"相态×类别×周期"聚合出基率（五口径：月分桶、阈值 5/20、任一档≥20 自动升 5 档、分化>5pp 强制子标签）→ calibration_view 出 Brier 分校准 → 周复盘消费 → 修订能力圈上限。

**反思层（您 10-08 指示补环）**：决策留痕（reasoning_trace+alternatives）→ 结果配对 → **18:45 反思作业**：代码先确定性组装**证据包** `GET /data/reflection_pack?decision_id=`（四段：S1 决策时点快照 / S2 证伪指标实际序列 / S3 归因证据 / S4 同相态基率对照），**缺口显式返回 gaps[]（如 FALSIFY_METRIC_MISSING/REGIME_MISSING），绝不静默填空**；指标路由表 route_map 观势有 PATCH 自修订权（版本留审计痕）；观势基于证据包写反思（四象限：对而对/对而幸/错而对/错而错；归因六类），产物=教训（candidate 认知）+行动项（即时生效）；下次决策先读反思日志。**无证据包的反思=无效。**
